Glacier Help & Feature Reference

Glacier is a modern, from-scratch level editor for Red Faction (2001) .rfl levels — a clean-room reimplementation (not stock RED.exe) that aims for stock-RED editor parity, Alpine Faction parity, and a layer of modern conveniences. This reference is fully offline; every link here jumps within the page.

Need a hand or want to share your work? Join the community on Discord (also on the Help menu).

1. Getting started

The first time you launch Glacier a short first-run wizard helps you point the editor at your game files. Nothing here redistributes game assets — Glacier reads textures, meshes and .tbl tables directly from your own Red Faction install.

The first-run wizard

  • Red Faction install — the folder whose .vpp packfiles hold the stock textures, meshes and tables. Optional: you can set it later in Settings, but textures and meshes will not resolve until it is set. Glacier probes common Steam/GOG and Wine locations automatically and reports how many VPPs it found.
  • Alpine Faction launcher — AlpineFactionLauncher.exe, the one executable play-tests run through. Glacier auto-detects it from the af:// protocol registration; otherwise browse to it. It may live outside the Red Faction folder.
  • Camera scheme — pick the navigation style you prefer (you can change it any time from the View menu). See Viewports & cameras.

Mounting game data

Once the install folder is set, Glacier mounts its VPP packfiles as a read-only virtual file system. alpinefaction.vpp is mounted above the base VPPs, so Alpine assets supersede stock ones exactly as the game resolves them. Use Tools ▸ Reload Textures / Reload Meshes to rescan without restarting.

Alpine Faction unlocks Alpine-only editor features, and multiplayer play-test launching runs through its launcher.

2. The interface

The workspace is a docked layout around a central viewport grid. Panels can be moved, floated, stacked into tabs and reset from View ▸ Reset Viewport Layout.

Docked panels

Outliner

Every object and brush grouped by type with counts, per-type and per-item show/hide, Jump To and View From. Sorted by name.

Properties

Context inspector for the current selection — brushes, faces, objects, events, lights, room effects, movers and more.

Asset Browser

Textures, meshes, sounds and prefabs: categories, filters, favourites, a large preview on hover, and drag any mesh or prefab straight into a viewport pane to place it where you drop it.

Object palette

Entities, clutter, items and event types, organised into category trees with hover mesh previews; drag a class into a pane to place it.

Link graph

An interactive node-graph editor of triggers, events, movers and their links — draggable, box-selectable, pan/zoom navigable.

Dependency graph

What references what: textures, meshes and assets used across the level, for packaging and cleanup.

Layers

Organise brushwork and objects into layers with show/hide/lock and solidity handling.

Statistics

Budget bars versus engine limits plus geometry counts, refreshed after every build and on demand.

Build output

The compile report — rooms, portals, faces, vertices, surfaces, lightmap pages, UIDs, timing and warnings.

Script console

A Lua REPL with history and colour-coded output; see Scripting.

Menus & the command palette

Everything lives on the menu bar (File, Edit, Select, View, Tools, Geometry, Level, Scripts, Help) and most commands are also on the toolbar. Press Ctrl+Shift+P for the command palette — a fuzzy search over every command that shows its bound key and runs it through the same dispatcher the menus use.

Notifications

Every message Glacier raises — a finished build, a warning, an error, a hint — always reaches the status bar and the Log panel. On top of that it can pop a brief toast in the bottom-right corner. Choose how much the toasts show from Settings ▸ General ▸ Toast notifications: Off, Errors only, Warnings, Info (the default) or Everything (including hints). The threshold gates only the toasts — the status bar and Log always record everything.

Undo application

Settings ▸ General ▸ Undo application sets how an undo is applied. Instant (the default) snaps straight to the target state in a single refresh; Replay walks visibly through each intermediate history entry. Both reach the same result — the choice governs plain Undo / Redo (Ctrl+Z / Ctrl+Y) as well as jumps through the edit history.

Locked brushes and objects are protected. Locking an item (the padlock in the Outliner or Layers panel, or Q / Shift+Q to lock / unlock) makes it unselectable and untransformable until you unlock it — a click that lands only on a locked item is refused with a hint — so you can work around fixed geometry without disturbing it. Unlock All (Shift+Q, or the Layers panel's Unlock button) also clears brush locks that shipped saved in the level file, so a file-locked brush becomes selectable and editable again.

3. Viewports & cameras

The viewport grid can show 1, 2 or 4 panes (cycle with F6, maximise the active pane with Tab). Each pane is independently a perspective 3D view or a top / front / side orthographic view.

Camera schemes

RED Classic

Stock RED navigation: numpad pitch / heading / slide, A/Z dolly, +/- ortho zoom, mouse-look on drag.

Modern FPS

WASD fly with mouse-look and a Shift speed boost — the default, familiar from modern editors and games.

Orbit

Tumble and dolly around the selection or a focus point, good for inspecting a piece of geometry from all sides.

UnrealEd

The UnrealEd-style mouse-button navigation many level designers already have in muscle memory: a left click selects, and a left drag flies the camera instead of drawing a selection box.

Continuous camera movement uses fixed held keys. The pitch / heading / slide / move-up-down / zoom / ortho-zoom motions are driven per-frame while you hold the key (numpad and A/Z/+/-). These are not rebindable — they appear in Settings ▸ Input for reference, and they are not offered in the command palette because a single click cannot reproduce a held movement.

Per-viewport view options

Each pane has its own options dropdown. Choices that apply to any view include Show Event Arrows (directional-event facing arrows, on by default), Show Links, Show Path Node Connections, Show Gizmo and Show Annotations. Perspective-only options include Draw Decals (project decal textures onto geometry; off by default), Draw Sky (draw the sky room like in-game), Show Fog, Room Rendering (scope which rooms draw) and Portal Faces (don't draw / see-thru / non-see-thru).

4. Editing modes

Glacier edits at several granularities. Switch modes from the toolbar, the View/mode hotkeys, or the palette.

ModeWhat you edit
BrushWhole brushes: create, move, clip, boolean, set brush type (solid / portal / detail).
FaceIndividual faces: extrude, bevel, texture and UV tools (the Texture/UV tab lives here).
VertexIndividual vertices: move, snap, weld.
EdgeEdges: bevel, extrude, collapse, loop / ring select, convert to faces or vertices.
ObjectPlaced objects and events: move, rotate, link, inspect, reorient, snap to camera.
GroupNamed groups of brushes and objects, moved and edited as a unit.
Edits keep every face flat. When a vertex, edge or face edit would bend a face off its plane, Glacier automatically triangulates that face — exactly as RED does — so brush faces never go non-planar. A move that slides along a face's own plane leaves it intact.
Selection follows the mode. Switching mode drops any selection the new mode cannot use — an object is deselected when you enter Brush, Face, Vertex or Edge mode. Group mode keeps both kinds: click a brush or an object to select it, and hold Ctrl to add across brushes and objects together. Clicking empty space, a locked item, or a wrong-kind item always clears the current selection.

5. Brush editing & operators

Brushes are the solid geometry of a level. Each brush carries a type that the compiler honours:

  • Solid — ordinary world geometry that walls off space and casts shadows.
  • Portal — a see-through boundary that splits rooms for visibility and culling.
  • Detail — decoration that does not carve the world BSP, so it never creates new rooms or leaks.
Portal brushes stay visible and selectable. An air portal brush (a portal that also carves) always shows its real textured faces, in every editing mode. A solid portal brush's faces instead follow the per-pane View ▸ Portal Faces option (don't draw / see-thru / non-see-thru). Either way, a portal brush is always selectable in every mode.
How an air portal brush builds. An air portal brush that cuts a doorway through a wall builds that doorway as a room of its own, with a portal at each end where it meets the rooms on either side — the same result RED gives. Portal brushes are applied after every other brush, whatever their place in the brush order. RED builds no portal from an air portal brush placed in an opening that is already carved; Glacier gives it one portal across its middle, and the linter warns about it (fit the portal brush through the wall instead, or make it solid). A solid portal brush carves nothing: its faces that lie in open space become a portal, as in RED.

Boolean and construction operators available on brushes and selections include boolean (subtract / intersect), clip, carve, fuse, stretch, bend, twist, mirror, n-gon split and bridge. The interactive Draw Brush tool builds a brush in three stages (base outline, then height) with live grid snapping; it starts each launch set to create Air (carve) brushes — toggle Air / Solid on the Brush panel. Opening or creating a level always returns the active tool to Select.

Increment-based transforms. Move (M), rotate (R) and scale (S) work by the grid / rotation / scale increment for RED-parity precision. Hold Alt during a mouse drag to temporarily invert the magnet snap state (snap ↔ free).
Air brushes are stored the way RED stores them. RED keeps an air brush's faces facing into the brush and a solid brush's faces facing out, and rebuilds a level from them as stored; Glacier does the same, so a level made or edited in Glacier rebuilds correctly in RED. Switching a brush between Air and Solid turns its faces around, as in RED; this does not change a brush's textures or what Glacier builds from it. A level saved by an older version of Glacier (or by another tool) can have air brushes facing out: the linter warns about each one, and saving the level in Glacier turns them around and says so in the save log.

6. Prefabs, groups & layers

Prefabs

A prefab is a reusable, parametric instance: save a selection of brushes and objects as a prefab, then place instances of it. Double-click a prefab tile (or drag it into a pane) to drop an instance in front of the camera, just like placing a mesh. Instances remember their source and their placement, so when you update the prefab you can propagate the change to every placed instance while keeping each one at the position and rotation you gave it. Update from Selection targets the prefab the selected objects belong to (or lets you pick one from a list) — no typing — with a prompt before overwriting instances you have modified locally. Prefabs live in your prefab library, browsable with thumbnails and a large hover preview.

A placed instance selects as one unit. Clicking any member selects the whole instance, and moving or rotating it drives every member together while keeping the instance's pose record current. To edit an individual member, double-click it — or click the padlock badge shown on the selected instance — to step inside; Esc (or clicking empty space) steps back out to unit level. Capture a new prefab from whatever is selected with File ▸ Save Selection As Prefab.

Groups

Groups bind brushes and objects into a named unit you can select and move together, import and export as .rfg files, and drag-drop into the viewport. Clicking any member selects the whole group as a unit; hold Alt to select the individual member instead (Ctrl likewise falls through to the single member, adding it to the selection). Locking a group protects every member from selection, movement and deletion until you unlock it, exactly as locking an individual item does.

Layers

Layers organise the level for authoring — show, hide and lock whole layers, with correct handling of brush solidity so hiding a layer never changes the compiled result.

7. To-Mesh conversion

Convert To Mesh Object turns selected brushwork into a static mesh object, matching the stock mesh-export behaviour. The To-Mesh dialog exposes the two toggles the conversion previously hard-wired, so you can control how faces and materials are emitted. Use it for decorative geometry that should render as a mesh rather than carve the world.

8. Objects & events

Objects are everything that is not world geometry: entities, items, clutter, lights, triggers, movers, particle emitters, ambient sounds, decals, cutscene path nodes, room effects, EAX environmental-audio zones and the full catalogue of events (148 event types).

Placing objects

Drag a class straight out of the Object palette (entities, clutter, items, events) or a mesh / prefab out of the Asset Browser and drop it into any viewport pane. A translucent ghost of the asset follows the cursor so you can see exactly what will land where. Dropped on a surface the object bottom-aligns to the face under the cursor (a pickup item instead floats 1 m above it); dropped in open space it lands in front of the camera. You can also place at the camera from the palette, staple an object to a face with S, or drop the last-placed kind at the cursor with P.

A new object's script name starts from a sensible default — the class name for entities, clutter and items, or the object type's name for everything else — and stays editable. Mesh objects can reference .v3m, .v3c and .vfx effect meshes, and .vfx files appear in the Asset Browser's Meshes tab alongside V3M / V3C models.

Every level needs a spawn point. A level's single Player Start marks where single-player begins; a new level is created with one already in place. Player Start (Move) in the Object palette moves it to the placement point — and creates one if the level has none. A level with no Player Start and no multiplayer respawn points has nowhere to spawn and renders black in-game; the level linter (Tools ▸ Run Level Linter) flags this.
Spawns stand 1 m above the floor. Multiplayer respawn points, the Player Start and Ground or Water waypoint helpers belong about 1 m above the floor, so the player or vehicle that appears there starts clear of it; Air waypoint helpers belong in open air. Place At Cursor (P) and dragging one of these from the Object palette onto a floor stand it 1 m up along the floor's normal (a wall hit, or a drop into open space, is left as is). The level linter warns when one of them sits less than 0.5 m above the floor below it or is inside solid geometry; it measures the compiled geometry, so build the level first. Scripted placement (level.place) uses the coordinates it is given, and the linter reports them the same way.

Inspectors

The Properties panel shows a purpose-built inspector for each kind — events (with their typed fields and schema), lights, ambient sounds, coronas, meshes (including a per-slot texture override editor), EAX effect zones (environmental-audio reverb regions, each with a labelled inspector, listed in the Outliner like any other object) and Room Effects (sky / liquid / ambient-light, with the full liquid-property field set). Multi-selection edits apply across the selection with mixed-value handling. Every edit is a single undo step.

Alpine Faction 1.5 objects

The Alpine group of the Object palette also places Alpine Faction 1.5's objects, with Alpine RED's defaults, fields, choices and limits. Each has its own icon, and the viewport draws what Alpine RED draws:

  • Weather Region — a box or sphere that rains or snows: shape and size, density, how far it is active and visible, whether geometry blocks it, and the rain or snow colour, speed, wind, sway and snow bitmap. Its volume shows while it is selected, with Always Show Range, or with Show All Ranges.
  • Vehicle Factory — spawns a vehicle or turret class (multiplayer) facing along its arrow: respawn delay, team, lock to team, spawn at level start, and for a turret a yaw limit, drawn as two yellow stops either side of the facing.
  • Projection Camera — the view a Display_Projection event renders into an animated texture. Link the event to the camera; the camera's frustum shows the event's field of view and render size.
  • Rope Emitter — a rope or zip line hanging to its target (any object; with none it dangles): slack, dangle length, segments, thickness, colour, bitmap, glow, dynamic, sway, zip-line speeds and direction, and decoration meshes duplicated along the rope (list up to six mesh files separated by ;, then set the count, spacing and order). The viewport draws the rope's resting curve.
  • Directional Light — parallel light travelling along its arrow, optionally bounded by a box (turned by Box Yaw), sphere or cylinder with a feathered edge, for Alpine RED's lightmap bake.
  • Waypoint Helper — a navigation point for vehicle bots: air, water or ground, the largest vehicle a ground route takes, a radius, and a landing / exit flag. Link helpers to each other with K to make routes (at most 64 per helper).

They move, rotate, copy, paste, duplicate and undo like every object, and a multi-selection of one kind edits all of them at once (except the script name). A pasted set of waypoint helpers keeps the links between the copies.

Terrain. An Alpine Terrain (Alpine group of the palette) is a heightfield: a grid of up to 257 × 257 vertices, axis-aligned, whose position is its min-X / min-Z corner (moving it moves the whole grid; it never rotates). A new terrain is 129 × 129 vertices 2 m apart, flat, centred where you place it. The Properties panel edits its cell size, height minimum and range, chunk size, lightmap density, Geoable (closed chunks geomod can carve — also turn on Brush-based geomod in Level Properties ▸ General), Skirts (walls below the edges and holes), Fullbright, thickness, skirt depth, the underside and crater textures, and its texture layers (up to eight names separated by ;, the first being the base). The viewport draws a terrain as Alpine Faction 1.5 draws it on Direct3D 11: its layers blend smoothly by their painted weights, overlays lie over them, its decorations stand on it and its baked lighting shows. Heights, the grid size, holes and heightmaps can also be set from scripts and AI tools: level.terrain.create{…}, then t:set_heights(function(x, z, wx, wz) … end), t:generate{seed = 3, type = "hybrid", height_range = 24, falloff = "island"}, t:resize{nx = 257, nz = 257}, t:set_layers{…}, t:set_hole(x, z, true), t:import_heightmap("map.png") / t:export_heightmap("map.png") (a greyscale PNG or RAW16; image row 0 is the +Z edge), t:height_at(x, z), and t:surface_at(x, z) (nothing over a hole or outside the terrain), t:set_holes(…) to cut many holes at once. Scripts can let the design kit decide between brush and terrain ground (see Brush or terrain ground).

Build Geometry compiles each terrain into detail rooms, one per chunk, and records them so Alpine Faction 1.5 recognises the terrain in game and draws it blended on Direct3D 11 (other renderers show each cell's main texture). Terrain does not seal a level or form rooms: keep it inside air (a sky box), or nothing collides with it — the linter says so. Air brushes do not cut terrain; use holes to open it. After changing a terrain, rebuild before saving: a terrain changed since the last build is saved without its record, and the game then draws its old geometry without the blend (the Log panel notes it). Convert to Brushes (the Outliner's right-click menu, or t:to_brushes{keep = false}) turns a terrain into one detail brush per chunk, for levels that must not use terrain; it is one undo step. Calculate Lighting bakes a light chart for every built terrain (not Fullbright ones), with shadows from the level and the sun, and saves it the way Alpine RED does, whichever lighting pipeline the level uses, and Alpine Faction 1.5 lights the terrain with it on Direct3D 11. Terrain lighting from Alpine RED is kept until you rebuild or relight; a terrain changed since its lighting was baked is noted in the Log panel at save. Decorations set to cast shadows do not shadow the terrain in Glacier's bake.

Terrain Tools. Select one terrain and the Terrain Tools appear at the top of the Properties panel (Alpine RED's Terrain Tools window). Turn on Paint in the viewport, pick a tool and drag on the terrain; clicks elsewhere select as usual, and a ring on the surface shows the brush (the inner ring is where the falloff starts).

  • Paint Layer / Erase to Base / Smooth Weights blend toward the layer chosen in the Layer list, toward layer 1, or toward the neighbours' blend. Choose an overlay or a decoration in the list to paint its coverage instead.
  • Paint Holes / Clear Holes open or fill the cells under the brush. Geoable Chunks (geoable terrains) sets which chunks craters carve; the first chunk you touch decides on or off.
  • Raise / Lower move the surface by up to strength × radius / 20 per dab and keep going while you hold still; the height range grows as needed. Smooth Heights, Flatten (to the height where the stroke began) and Set Height (to the Height field; Ctrl+click picks up the height under the cursor) blend toward their target. Noise roughens by up to ± strength × radius / 4.
  • Ramp slopes the ground at the Angle field along your drag; Bridge Points lays a straight ramp from where you press to where you release.

Radius ([ and ] while the tools are on), strength, falloff (smooth, linear, constant) and spacing set the brush. Mirror X and Z repeat each dab across lines through the terrain's centre plus an offset; Shift+click places the lines. Each stroke is one undo step and Esc cancels the stroke in progress. A stroke that changes heights or holes marks the build out of date: rebuild before playing. Stitch Edges snaps the border to a neighbouring terrain of the same cell size. The Decorations group adds, changes and removes decorations (mesh, density, scale, slope, draw distance, offset, linked layer, flags); Show decorations hides them in the viewport. Generate... opens Generate Terrain: grid size, height range, noise type, seed, feature size, octaves, roughness, lacunarity, domain warp, exponent, terraces, offset and edge falloff, with a live height or shaded preview; Apply is one undo step. Glacier's generator has no erosion or splat-map options. Scripts and AI tools sculpt and paint with the same tools: t:sculpt{tool = "raise", path = {{0, 0}, {20, 5}}, radius = 6}, t:paint{layer = 2, at = {4, 8}}, t:set_decoration{mesh = "…", density = 0.4, coverage = 255}, t:set_overlays{…} and t:stitch().

Mover paths. With Legacy movers off (Level Properties ▸ Compatibility), a mover's keyframes can start curved segments. The Path group of the Keyframe panel (see Movers, keyframes & cutscenes) sets each keyframe's Segment (straight / curved), Handles (Auto, Aligned or Free), Easing and Segment Facing, and the mover's Mover Facing (None, Follow Path, Keyframe Rotation) and Riders options. Curved segments and a loop's closing segment are drawn in the viewport, and a selected keyframe shows its curve handles, which you can drag.

Liquid emission. A Liquid Room room effect can make its liquid surface glow for Alpine RED's bake: off, up only, or up and down, with a colour, intensity and reach. A copied room effect keeps it.

The level linter reports what Alpine Faction would refuse or ignore — a vehicle factory with no or an unsupported class, a rope whose target is gone, a Display_Projection event with no camera, path settings on a mover that cannot use them, emission on a room effect that is not a Liquid Room — and values Alpine loads clamped.

Links & the link graph

Wire triggers to events to movers by linking objects (K to link, Shift+K to break). The Link Graph panel visualises and edits these connections as a node graph; node positions persist per level in a sidecar next to the .rfl.

Movers, keyframes & cutscenes

A mover is one or more ordinary world brushes — a door, lift, elevator or rotating platform — bound into a moving group that animates along a keyframe path. The brushes stay normal, fully-editable world brushes; grouping them as a mover only adds the motion. Moving groups are listed and managed in the Moving Groups list.

Each mover follows a chain of keyframes. A new keyframe is seeded at the mover's own origin, lined up with the brush, and you drag it out to shape the path. Keyframes are real, selectable objects — they show in the Outliner and draw on top of geometry so they can always be clicked. Deleting a keyframe never removes the mover's brush; deleting a mover's last keyframe dissolves the mover back to static geometry. Dissolve (on the Moving Groups list) turns any mover back into ordinary static brushes at any time.

Movers are saved the way RED saves them, so a level opened in RED or Alpine RED keeps its movers when it is rebuilt there, and mover edits made in either editor carry over to the other. A level saved by an earlier Glacier is repaired when you open it; resave it to keep the fix. New keyframes are named "Keyframe", as in RED.

The Keyframe panel. Select any keyframe, or any brush or object of a mover, and the Properties panel shows the Keyframe panel — RED's Keyframe Properties dialog in two parts. Double-click a keyframe to open the same content as a window.

  • Mover (whole chain) — RED's Keyframe List Properties: Is Door, Starts Moving Backwards, Hold Open, Rotate in Place, Use Travel Time as Velocity, Force Orient, No Player Collide; Movement Type; Starting Keyframe (counted from 1, as RED shows it) with Preview; the Start, Looping, Stop and Close sounds, each with Browse…, a volume and a Preview button that plays it; and RED's three buttons. Propagate Sounds copies the four sounds and volumes to every mover that has a keyframe with this keyframe's script name. Propagate Properties copies the mover's flags, movement type and starting keyframe to those movers, and this keyframe's pause, travel, acceleration, deceleration, event and item UIDs and degrees about axis to every keyframe of that name. Both refuse a keyframe still named "Keyframe" (or with no name) and work from one keyframe at a time. Stop Sounds stops the sound preview.
  • This keyframe (n of N) — with ◀ ▶ to step along the chain (each step selects that keyframe in the viewport), Add Keyframe and Delete: Script Name, Pause Time, Departing and Returning Travel Time, Acceleration and Deceleration Time (all in seconds), Trigger Event With UID and Contains Item UID(s) (blank means none), Rotation Properties (Degrees about Axis), the Path group (Segment, Handles, Easing, Mover Facing, Segment Facing) and Riders. As in Alpine RED, Legacy movers greys the Path and Riders settings, Rotate in Place greys the path shape and facing, and Segment Facing needs a Mover Facing other than None. Mover Facing and Riders belong to the whole mover.

Select several keyframes of one mover to edit them together: a field whose values differ shows blank and keeps each keyframe's own value unless you change it. Every change is one undo step, and a new keyframe starts with 1-second travel and return-travel times, as in RED. Moving or rotating a whole mover in Object mode moves its brush with it as one undo step; its keyframes stay where they are.

Previewing a mover. Preview plays the mover in the viewport: its brushes and objects travel the real path — Alpine curves with Legacy movers off, straight segments with it on — with the game's timing (travel times or speeds, pauses, acceleration and deceleration, easing, the movement type's order, Rotate in Place, Mover Facing and Force Orient). Play / Pause, Stop, a scrub bar and a speed choice sit under Starting Keyframe; small ticks along the path mark equal steps of time, so they bunch where the mover is slow. The preview never edits the level: Stop returns the mover to its rest pose and nothing needs undoing.

Curve handles. A selected keyframe's curve handles (orange) can be dragged in the viewport; the handle under the cursor turns white. A handle moves in the plane facing the camera. An Auto keyframe becomes Aligned, and an Aligned keyframe turns its other handle to stay opposite. Each drag is one undo step; Esc cancels it, and Alt+click selects through a handle.

Driving a mover. Link a trigger or event to the mover to set it moving; the link attaches to the mover's start keyframe, which is the connection the game follows. In the Link Graph a mover's internal structure is drawn as dashed edges, distinct from real links. Cutscenes drive the camera along path nodes. Copy and paste preserve every field, and fresh UIDs are assigned to clones so nothing collides.

9. Textures & UV

Browser & library

The texture browser lists everything mounted from the game data plus your custom subdirectories (shown as Custom - <dir> categories), with filters, favourites, tiled preview and display-size control. Supported formats include TGA (incl. 8-bit greyscale), VBM, DDS (DXT1/3/5), PNG, JPG and ATX (frame 0), resolved through the same supersede chain the game uses.

Drop a texture onto a face. Drag a texture tile from the browser onto a brush face in a viewport to apply it. If that face is part of the current face selection the texture applies to the whole selection; otherwise it applies to just the face you dropped on — always in a single undo step. (A locked brush is refused.)

Mapping & UV

From the Texture/UV tab (in Face mode) apply Box (Ctrl+Q), Planar and Cylinder (Ctrl+W) mapping, set pixels-per-meter, copy/paste UVs, and flip. Box, Planar and Cylinder project in world space, not brush-local, so a texture tiles continuously across adjacent brushes however each is rotated. Two Fit buttons snap the mapping to the texture tile: Fit stretches the face corner-to-corner over the tile (world projection), while Fit (Keep Aspect) scales uniformly so the texture is not distorted. Verify Textures (Tools menu) reports faces whose textures are missing from the mounted data before you build or package.

Planar map is a toolbar button, not a hotkey. In the RED Classic preset Ctrl+E is Extrude in Face mode, so Planar map has no key — use the Texture/UV panel button.

UV Unwrap editor

The UV Unwrap editor (Texture/UV panel ▸ UV Unwrap…) opens a 2D view of the selected faces' UV layout over their tiled texture. Every edit — including one completed gizmo drag — commits as a single undo step.

  • Selection modes — choose Vertices, Edges or Faces from the toolbar; the stored selection survives a mode switch. Click to pick, or drag a rubber-band box — hold Ctrl to add and Alt to remove.
  • Transform gizmo — hold M (move), R (rotate) or S (scale) with a non-empty selection to show a 2D gizmo at the selection centroid: drag the axis arrows or centre square (move), the rotation ring (rotate), or the axis boxes and centre/corner handle (per-axis vs uniform scale). The arrow keys still nudge by the increments while the key is held. With Grid Snap (G) on, a move lands the selection's centroid on the grid step and a rotation snaps to the Rotate° step; with it off both are continuous.
  • Increment selectors — the Rotate° and Grid toolbar controls are preset dropdowns with free entry, matching the main window's rotate/grid pickers; Move and Scale stay free-entry boxes.
  • Layout tools — Flip V/H, Align (Shift+V / Shift+H), Auto Unwrap (planar-project and pack the faces into the tile), Fit UVs (scale the selection to fill the base tile), decal-vs-texture display (D / T), Show Tiled, and Print → TGA.
  • Multiple faces — unwrap more than one face at once and each gets its own colour and a numbered label so you can tell them apart; hovering a face shows a readout and cross-highlights the matching face in the 3D viewport.
  • Navigation — wheel or Shift+right-drag to zoom, Shift+left-drag or middle-drag to pan, and Fit View to reframe.

10. Geometry building

Building compiles your brushwork into the room/portal BSP the engine renders. Run it from Geometry ▸ Build Geometry (Space in RED Classic, Ctrl+B in Modern).

Build Method

Shared BSP (default)

RED's authentic single accumulated shared BSP — the RED-faithful method, on by default. Measured equal-or-better than Incremental on every corpus level.

Incremental

Glacier's own modern accumulator. Fully functional and selectable from Geometry ▸ Build Method — nothing is removed.

Repair Holes When Building

Geometry ▸ Repair Holes When Building (on by default) repairs the small holes a build can leave, the same way Alpine Faction's level editor does: where brushes sit flush against each other or a portal is cut along a wall. With it on, every full build:

  • welds the ends of open edges that lie within 1 mm of each other, and splits an edge where another face's corner lies on it;
  • removes zero-area faces and zero-width portal strips left along seams;
  • puts a portal face back in the room it faces, restores a lost portal face, and joins rooms that were split apart without a portal between them;
  • fills small flat gaps in a wall (up to 1 square unit, at most 16 corners, convex, flush with the wall around them, and never in a doorway) with a new face that continues the wall's texture. A filled face has no lightmap.

Detail brushes and movers are never changed. The live preview skips the hole repair (it is unsealed anyway); the full build, saving, Check for Holes, scripts, and the command-line tools all use the setting. The repair's figures appear in the build report under Repairing holes.

Check for Holes & the build report

Check for Holes looks for leaks — gaps where the world is not sealed. It always checks a full build, so with Repair Holes When Building on it reports what is left after the repair; it never repairs anything itself. The build report (Build Output panel) lists rooms, sub-rooms, portals, faces, vertices, surfaces, lightmap pages, UIDs, elapsed time, the hole-repair figures and any warnings. The warnings are textual; hole-leak findings are click-to-navigate — click one to frame the leak in the viewport.

Saving never rebuilds or re-bakes. A save (Ctrl+S) writes exactly what you last built — RED-style — so rebuild geometry and recalculate lighting yourself after you change them. The one exception is an automatic re-seal of unsealed live-preview geometry immediately before the write (which resets its lightmaps to unbaked). If a build is still running the save is aborted — "retry when it finishes" — rather than writing half-built geometry.

11. Lighting

Glacier bakes lightmaps from your placed lights. Run a bake from Build ▸ Calculate Lightmaps (L) or the combined maps-and-light command. The Preview Lighting toggle re-bakes small levels with the exact CPU kernel for an accurate in-editor preview.

Edits keep the existing bake. Editing geometry after a bake does not throw the lightmaps away — the surrounding preview rebuild keeps them in place, now stale, until you recalculate lighting, exactly as RED does. Recalculate when you are ready for the shading to catch up.

Lightmap Method

The Level ▸ Lightmap Method flyout stays open while you toggle options. Pick one base method, then layer on any modifiers:

Level Properties

Level ▸ Level Properties has Alpine RED's six tabs, with its groups, labels and helper buttons. Edit freely: OK writes every change as one undo step, and Cancel writes nothing.

  • General — Level name, Author, the Date (set on save) and the RFL version, Multiplayer level; Level Flags: Outside and Inside flag every room of the level (every room effect's Room Is Outside and the built rooms) at once, after RED's warning, as their own undo step; GeoMod: texture (Browse…), level hardness (0 = large craters, 100 = no craters), brush-based (RF2-style) geomod; Require Direct3D 11 Renderer.
  • Lighting — Ambient Light and Distance Based Fog colours (a swatch, Change color, the editable <r, g, b> text, and Default for RED's new-level ambient), the fog's near clip (Direct3D 11 only; OK pulls it just below the far clip), far clip and the camera far clip (0 = the fog far clip); the static-mesh ambient override and its scale; and Sunlight: enable, Set from camera (aim the active 3D view the way the sunlight should travel), yaw, pitch, intensity, spread, colour and its five options.
  • Lightmaps — High-resolution lightmaps, the four Light Blocking options, D3D11-only lightmaps (greyed with Legacy lighting or density Off), Lightmap density and Compression.
  • Gameplay — Player starts with headlamp, the vehicle flight ceiling, and the Payload rules with the attackers' and defenders' respawn delay modifiers.
  • Minimap — Enable minimap, the bitmap (Browse…, with a preview), its world bounds and cut height. OK checks them as Alpine RED does: an enabled minimap needs a bitmap, the bitmap is a bare file name, and the bounds are at least 1 m across. Baking the minimap from the level is done in Alpine RED; Glacier shows those controls greyed.
  • Compatibility — Legacy Cyclic_Timer events, Legacy movers, Legacy lighting.

Alpine Faction 1.5 lighting settings

The Lighting, Lightmaps and Compatibility tabs of Level Properties hold the settings Alpine RED's own lightmap bake reads: Legacy lighting (the stock pipeline instead of Alpine's), High-resolution lightmaps, lightmap density and compression, D3D11-only lightmaps, which faces and meshes block light, and the sun (direction by yaw and pitch, colour, intensity, soft-shadow spread, and how it lights meshes). A brush's No Shadow Cast option (detail and mover brushes) leaves it out of the baked shadows. Glacier's Calculate Lighting bakes with all of them, as Alpine RED does:

  • High-Res Lightmaps bakes the stock lightmaps on 256×256 pages at four times the density (fragments up to 254 texels); it needs a Build Geometry, with either pipeline.
  • Lightmap compression picks how the Alpine lightmaps are compressed (BC7, as Alpine RED ships them): Quality is plain BC7; Balanced and Compact trade a little accuracy for a smaller file.
  • D3D11-only lightmaps: when the level has Alpine lightmaps, the save leaves the stock lightmaps out (smaller file) and the level needs Alpine Faction on Direct3D 11; movers without Alpine lightmaps then draw fullbright, and the Log panel names them. Glacier keeps the stock lightmaps in memory, so turning the setting off and saving writes them again.
  • With Alpine lighting, shadows use Alpine's rules: Invisible Faces Occlude (they block light reaching their front), Alpha Faces Occlude (faces with an alpha texture), Alpha-Tested Occlusion (grates and fences cast patterned shadows through their holes), Meshes Occlude (Alpine mesh objects cast shadows, unless the mesh's No Shadow Cast is set), and No Shadow Cast brushes cast none. A mover is shadowed by its own brushes only, as in Alpine RED.
  • Liquid emission on a Liquid Room room effect makes its liquid surface glow: what lies within the distance above it (and below, with Up And Down) is lit by the surface's colour and intensity, shadowed by whatever stands in between.

Lightmap Pipeline (Alpine lightmaps)

Each level stores its lightmap pipeline as Alpine Faction does, in its Alpine level properties. 12. Scripting (Lua)

Glacier embeds a Lua scripting engine exposed as a safe, versioned facade over the editor. Open the Script Console (a REPL) or the Script Editor window (syntax highlighting, Run / Dry-Run / Run-Selection). Scripts live in the portable scripts\ library beside the app, and ship with an example gallery (array grids, spiral stairs, mass texture replace, and more).

Calculate Lighting (No Shadows) bakes the way RED's own no-shadows command does: every light lights every surface within its range, straight through walls and floors, so rooms near bright or numerous lights come out at full strength or brighter. Use it to check where light falls; judge brightness, mood and dark areas only after a full Calculate Lighting. The sky room is drawn full-bright in the Lit view, as in the game: its baked lightmap is not shown, so a sky box needs no lights of its own.

  • One run = one undo step. The whole run is a single undo transaction: success commits one undo node; an error or a Dry-Run rolls everything back, so a failed script leaves the level untouched. To recover from an error inside a script, call local ok, result = ged.try(fn, ...): when fn fails, everything it changed is undone and result holds the error (message, hint), so the script can try again, for example with another seed. Time limits and Stop still end the whole run.
  • Auto-registered commands. A user script with a --@name/--@id header registers itself as a command in the palette and Scripts menu, optionally bindable to a key with --@key.
  • Sandbox limits. No file, network or process access; runaway loops are bounded by an instruction budget and a timeout; destructive operations require an explicit allow-destructive opt-in and are disabled in Dry-Run.
  • Builds match the editor. ops.build() and ops.light() use your Geometry ▸ Build method, Repair Holes When Building setting and Lightmap Method, exactly like the toolbar commands, and the viewport shows the result when the script finishes; the returned report's repair holds the hole-repair figures. ops.check_holes() returns the leak count and ops.holes() returns their positions, always measured on a sealed build.
Lua ops.playtest is editor-only. In the editor it saves the level and launches it through the same flow as Play Level once the script finishes (it needs the allow-destructive opt-in, like ops.save); outside a running editor session it raises an error. The full API — ged, level, selection, assets, ops, lint, log, rng, catalog, prefab and the design kit — is documented in the Scripting API Reference (Scripts menu), generated from the API itself so it always matches your build.

Building levels from scripts

Scripts that declare --@api 2 (or call ged.require_api(2)) can build and edit a level with table arguments; older scripts keep working unchanged. Units are metres and degrees; +X is right, +Y up, +Z forward; print(ged.conventions) lists every rule.

  • Brushes. level.brush{shape = "box", pos = {0, 2, 0}, size = {8, 4, 8}, air = true} creates any primitive (box, cylinder, cone, sphere, wedge, quad) at the end of the CSG time order. Remember the world starts solid: an air brush carves a room, a solid brush adds geometry, and later brushes win. Brush handles move, rotate, scale, clip, carve, copy and re-order, and map UVs (box_map, planar_map, fit, …); without a ppm value the mapping functions tile one repeat per 4 m, like a brush drawn in the editor (box_map(256) maps at RED's 256 pixels per metre). textures = {floor =, wall =, ceiling =} are as the player sees them. To line textures up, face:align_to_edge("bottom") stands a face's texture on its lowest edge ("top" hangs it from the highest; an edge number or "+x" … "-z" picks another), face:wrap_from(other_face) continues a neighbouring face's texture around the corner, and brush:fit_faces() fits one texture repeat to every face of a crate, panel or door however it is rotated (fit_faces{axes = "v"} fits only the height, for a trim strip). level.uv_align{} lines up the textures of every brush (or brushes = a list or query, or selection = true) the way a mapper does by hand, as one undo step: floors and ceilings share one map, wall textures stand on the floor line, wrap around corners and fit their height to whole repeats, ramps and rock map at true length with the texture folded across every edge, and no wall reads mirrored; faces already fitted to whole tiles are kept. Beams, posts, pilasters and rails get a girder or trim texture laid along their length, as stock levels do, with no repeat across a narrow face; ones already textured that way (library modules) keep their mapping. catalog.texture_info(name).grain tells which way a texture's features run. It never runs on a level by itself. level.uv_report{} measures the same things without changing anything and lists the worst places (mirrored walls, broken seams, stretched slopes, girder textures stacked across a post) with their positions; AI assistants have both in the align_textures tool (report = true only measures).
  • Objects. level.place{kind = "item", class = "Medical Kit", pos = {0, 0.5, 4}} places any placeable kind with a name, rotation (yaw or rot = {yaw, pitch, roll}), properties and links in one call. Every object, brush and mover reads and writes its Properties-panel fields with get / set / set_many; fields() lists them. level.player_start{…} places or moves the Player Start.
  • Links, movers, groups, prefabs. link_to / link_many / back_link follow the editor's link rules (a link to a mover is stored on its start keyframe); level.create_mover{…} and mover:add_keyframe{…} build movers, and mover:propagate_sounds(kf) / mover:propagate_properties(kf) are the Keyframe panel's Propagate buttons; level.create_group{…} groups parts; prefab.list() and prefab.place{…} use your prefab library.
  • Level properties. level.props (name, author, multiplayer, ambient light, fog…) and level.alpine (Alpine Faction level options, including the payload_* rules); level.set_all_rooms_outside(true / false) is the Level Flags Outside / Inside buttons.
  • Discovery. catalog.kinds(), catalog.classes("Item"), catalog.describe("Event", "Explode") and catalog.textures("rock") list what can be placed and how to configure it (entity, item and clutter classes need an RF install mounted); ged.describe("brush") lists a type's members, including every key a table argument such as level.brush{…} accepts, with its type and default. Unknown names and keys are errors that suggest the nearest valid one; every error names the line of your script that made the call. catalog.norms("opening.width") gives the typical range of a measurement across released levels (see glacier-cli norms; catalog.norm_metrics() lists them); catalog.norms_for{metric = "lights.per_100m2", gametype = "dm", players = 16} picks the numbers for a kind of level (deathmatch maps are also measured by size), falling back to the general ones.
  • Tags. b:tag("area", "arena") attaches your own labels to brushes and objects (saved with the level); level.brushes_tagged("area") finds them again.
Movers keep their own brush copy. A mover copies its member brushes when it is created; the build and the game use that copy. Whenever a mover's brush is edited afterwards — in the viewport or by a script — the copy is refreshed automatically before the level is built, saved, packaged, or playtested, as part of the edit's undo step (scripts also refresh it before ops.build, ops.light, ops.save or ops.package and when the script finishes; the Script Log notes it). mover:sync() refreshes it at any other point. Movers whose brushes you did not edit are left exactly as they are.

Modules and the design kit

ged.import(name) loads a Lua module once per run (once per session in the Script Console) and returns it. Glacier ships the design kit; your own modules go in the scripts library's lib\ folder as <name>.lua (module files are libraries, so they do not appear in the Scripts menu). A script run from a file with glacier-cli run (or the MCP run_lua tool's file) can also import the .lua files beside it that it names with a literal string, such as ged.import("graph"): that folder only, never a sub-folder or a parent, and the modules travel with the run, so a run sent to the editor works the same. Scripts run from the Script Editor import from lib\ only. A module runs in the same sandbox, limits and undo step as the script that imports it.

local kit = ged.import("kit")
local hall  = kit.room{ name = "hall",  pos = {0, 0, 0},  size = {16, 6, 16} }
local annex = kit.room{ name = "annex", pos = {15, 0, 0}, size = {12, 6, 12} }
local way   = kit.doorway{ name = "annex_way", a = hall, b = annex }
kit.door{ name = "annex_door", opening = way, buttons = { {7.5, 1.5, 2.5} } }
kit.light_room{ room = hall }
kit.spawn_points{ room = hall, count = 2 }
  • Functions. kit.room, kit.corridor (between two rooms or along a path), kit.doorway (optionally a portal doorway: the opening becomes a portal brush that cuts the wall, as RED builds portals), kit.stairs, kit.ramp, kit.door (a sliding mover door with use-key buttons or an automatic trigger), kit.platform, kit.pillar_row, kit.light_room (each light hangs under a visible fixture, a corridor gets a single row, and lights never land inside a pillar or other solid in the room), kit.spawn_points (spawns spread at least 8 m apart beside cover, clear of doorways and facing the way out) and kit.sky_room (an outdoor sky: a small sealed sky box with a Sky Room effect, and show-sky ceilings over the rooms you list — the way the stock levels build their skies), and the organic functions kit.cave, kit.canyon, kit.passage, kit.rock_wall, kit.boulders, kit.pit and kit.light_path (see Caves, canyons and rocks). Stairs come with an invisible collision ramp over the step edges so players walk up them smoothly. print(kit.help()) lists every function with its options.
  • Textures. Kit brushes are box-mapped in world space at 64 pixels per metre of each texture's real size, the texel density of Red Faction's own levels: a 256 px texture repeats every 4 m, a 128 px one every 2 m. Rock is mapped the same way. Without an RF install mounted every texture counts as 256 px (one repeat per 4 m). Change kit.defaults.ppm, or set it to nil to tile every texture at kit.defaults.tile_metres. Kit stairs start each tread's texture at its nosing, and ramps run theirs up the slope without stretching. Every kit part's textures are then lined up as level.uv_align does, and kit.build_layout lines up the whole layout at the end so textures continue from one part into the next; set kit.defaults.uv_align = false to keep the plain box map.
  • Palettes and trims. kit.palette{theme = "industrial"} (also "bunker", "admin", "cave", "marsbase") returns a coherent set of stock textures for a zone; pass its textures to kit.room, use variant so neighbouring rooms differ, and team = "red" or "blue" for team-coloured frames and accents. kit.trim{room = hall} gives a room a base band, a top band, posts every few metres, frames around every doorway and window through its walls, and hazard stripes along the open edges of kit platforms. Build it after the room's openings and the solids standing in it.
  • Spaces and set pieces. kit.space{archetype = "atrium", pos = {0, 0, 0}} builds a complete space at the proportions of well-liked multiplayer levels: a hall, atrium, arena, ring, sunken court, stair hall, courtyard, canyon with a bridge, cave chamber, pit room, control room or storage hall; an open-air platform, sky bridge or open deck; or a Payload cart road, overlook, gate or finale. kit.archetypes{} lists them with their sizes. A kit.room whose size leaves out the height (size = {16, nil, 12}) gets the height kit.proportion gives for its footprint. kit.shaped_room makes rooms that are not boxes (octagon, L, T, U, cross or any polygon, with chamfered corners and stepped, gabled, shed, coffered or beamed ceilings), and kit.alcoves, kit.pilasters and kit.floor_section add wall insets, piers and raised or sunken floors. kit.bridge, kit.truss, kit.beam and kit.landmark make structures at landmark scale (a bridge warns when its span is under 12 m or its drop under 6 m), kit.opening cuts windows, arches and rough mouths between two spaces, and kit.road lays a wide, graded Payload cart road with level turns and tunnel legs.
  • Population. kit.dress{room = "hall", theme = "industrial"} fills a room, corridor, cave or canyon with props, cover, overhead beams and pipes, decals and (with the game tables loaded) stock clutter for a theme: "industrial", "construction", "storage", "control", "mine" or "canyon". Props come in groups (crates with barrels or a toolbox beside them, a barrier with crates at its end), gather in corners and along walls, and frame each doorway; no decal goes where it would touch a compiled face with more than 19 vertices, which crashes the game and the editor when the level loads (the linter reports any such decal as an error). kit.spawn_points{rooms = {hall, annex}, count = 8} places sheltered spawns that few others can see, and kit.items{gametype = "ctf"} places weapons, ammo, health, armour and powerups for dm, tdm, ctf, koth, cp or payload (place the spawns first): about 1.6 items per 100 m² on a deathmatch-sized level, fewer per area on large levels, and never bunched. kit.light_room hangs its ceiling fixtures from the ceiling over each one; a room open to the sky gets a few strong lights on its edges instead (lamps on the walls, a lamp post beside each doorway, none standing on the way between doorways), and kit.light_path mounts each light on a wall lamp. All three take a seed, accept a room by its name, and keep walking routes, doorways and spawns clear.
  • Floor-anchored. Every kit pos is a point on the floor, and a room's size is its clear interior. Openings meet rooms exactly, so the result is watertight and stays grid-clean for hand editing. Walkable openings narrower than 1.8 m or lower than 2 m are refused unless you pass allow_tight = true.
  • Easy to keep editing. Kit output is ordinary editor content: plain brushes tagged with what made them (kit, kit.name, kit.part), named objects, and named groups for multi-brush parts such as stairs.
  • Customising. Change kit.defaults (corridor and door sizes, step size, light spacing, …) from your script, or copy lib\kit.lua to lib\mykit.lua and ged.import("mykit"). The name kit always loads the version built into Glacier.
  • Example. Example: tiny deathmatch level (design kit) in the example gallery builds three rooms, a corridor, a button door, stairs, pillars, lights, spawns and items on a new level, and checks it is watertight. Example: textured zones (palettes, trims, aligned UVs) shows palettes, trims and the texture tools.

Builds use your Geometry ▸ Build method and Lightmap Method from Settings, and saves follow File ▸ Save exactly (Alpine v306, a re-seal of preview geometry first, the level's sidecar). Textures and game tables come from a Red Faction install: --rf-dir <dir> first, then the GED_RF_DIR environment variable, then the install configured in Glacier's settings (the settings.cfg beside glacier-cli, else the one in your profile). --verbose reports which install was mounted and where it came from; without one, renders use flat colours and class and texture names cannot be checked.
  • The level's sidecar. Every save — File ▸ Save in the editor, save, run --save/--out, build --save — also writes <level>.gedlayout.json beside the .rfl. It holds editor-only data: Link Graph node positions, measurement annotations, and the level's own lightmap method when it overrides the global one in Settings. The game never reads it, packfiles leave it out, and the level works without it; keep it next to the level to keep those editor settings, or delete it to drop them.
  • Attach mode. With Settings ▸ General ▸ Allow command-line tools and AI agents to control the open level on (the default), --attach sends the command to the open editor: script output appears in the Script Log, the viewport updates, and each run is one undo step. Leave out the level argument to use the open level. Nothing ever shows a dialog; replacing a level with unsaved changes needs --allow-destructive. Rendering images

glacier-cli render never changes the level. It draws the level's compiled geometry; if the level has never been built, or its brushes changed since the last build, it makes a quick preview build for the image only and says so. --rebuild or --sealed force a fresh preview or sealed build. With --attach it draws the level open in the editor, unsaved edits included — the editor hands glacier-cli a copy, so rendering never slows down or alters your session. The image is written wherever --out points.

Floor heights. Flat floors carry a spot height (+2.5). Steps a player walks up are not marked. Matching reference screenshots

When a level is built from concept art, glacier-cli ref compares the level with each screenshot from a matching camera, so you (or an AI agent) can see exactly where the build differs. The references live in a folder of your choosing (--refs <dir>: one PNG per reference plus references.json); the level itself is never changed. The same operations are the MCP tools reference_view, reference_edit and reference_compare, and the scale table is the MCP resource glacier://reference/scale.

Recreating an area from an overhead picture

For a map, mockup or drawing seen from above, the Lua ref global measures the picture and the design kit's kit.trace builds it literally:

  1. ref.open(picture) and ref.grid{crop = {x, y, w, h}, zoom = 4, out = "grid.png"}: the picture with every grid line labelled in its own pixels, to read corners exactly.
  2. ref.calibrate{bar = {x1, y1, x2, y2, metres}, origin = {px, py}, at = {x, z}}: pixels to metres from a scale bar or a known length (the top of the picture is +Z, north up); ref.to_world, ref.to_px and ref.world_points convert.
  3. ref.mask{samples = {{x, y}, ...}} (optional): the playable area picked by colour, cleaned, and traced into outline polygons (holes kept, or cut into hole-free pieces), with an overlay to check it. mode = "hsv" separates painted rock from tiles, split gives pieces per colour or zone, and ref.mask_edit{fill = ..., erase = ...} corrects the mask. ref.grid{overlay = plan} draws your trace (or "level", the built floor) over the picture to check every corner.
  4. kit.trace{units = "px", regions = {...}, openings = {...}, solids = {...}}: every region is a polygon of any shape with a floor and a ceiling or open sky (rooms, corridors, yards, pits, ramps and stairs, decks over a void); openings cut doorways through the wall between two regions; solids are pillars and machine footprints. Nothing is reshaped or linked; overlapping regions, an opening that is not between its regions, an impossible ramp and a crossed outline are refused with the reason. Where the picture shows rock, a region can be a "canyon" or "cave", a path can be a rough tunnel (organic = true), and any wall can be rock (rock_edges, walls = "rock"), with mounds, terrain and boulders on the floor. Rock walls are eroded: they lean in and out in tiers, with buttresses, ledges carrying scree and overhangs above head height, and a cave's ceiling is one hanging vault. The traced outline is kept, and kit.rock_mass raises mesas and outcrops from an outline, with a talus apron and rounded strata. The plan is built like a generated layout that follows your design: the layout check reads its walk graph (layout_check), traced stairs and ramps are the kit's own (named in the warnings when they climb into a wall), doorways get frames, walls get trims, ceilings get beams, drops get railings, and every zone gets lights (via = "prism" builds the bare plan). A ramp region may have any outline — a corridor that widens as it climbs — with one sloped floor from its foot to its top and, standing on its own, a ceiling parallel to that floor.
  5. Heights: when the picture is a heights render (--mode heights, or a plan with the heights overlay), ref.heights{legend = {min, max}} reads it back into a height grid, flat floors, ramps, stairs and drop edges, as regions ready for kit.trace{units = "px", regions = h.regions}, and writes a check overlay with out.
  6. ops.build() then ref.compare{out = "cmp.png"}: the level's walkable floor drawn on the picture (missing red, extra orange) with the overlap, the wall error in metres and the largest missing and extra regions. Fix the worst region, rebuild and compare again.
On Linux, glacier-cli is included in the tar.gz package (the AppImage starts the editor).

The module library (glacier-cli modules)

A module is a small hand-built assembly — a pilaster, a base trim, a door frame, a ceiling beam or truss, a railing, a pipe, a machine, a rock formation — saved as a group file with a description of how it attaches and how it may stretch. The design kit's detailing functions (kit.wall_detail, kit.frame_opening, kit.ceiling_detail, kit.detail and the others) build with modules from a module library.

glacier-cli modules harvest builds the library from levels you choose. It reads each level (loose .rfl files, and the levels inside .vpp packfiles) without changing it, finds the detail that recurs, merges near-identical copies, and writes one .rfg group file per module — it opens in the editor like any saved group — plus an index.json per source group that lists each module's category, role, attachment, stretch and repeat axes, style, textures, size, and the level and position it came from.

glacier-cli modules harvest --rf-dir "C:\Games\RedFaction"
glacier-cli modules harvest mylevel.rfl --group mine --out library\modules
glacier-cli modules stats
glacier-cli modules list --category pilaster --style bunker --limit 10
glacier-cli modules show pilaster_04f7c88b
glacier-cli modules sheet --rf-dir "C:\Games\RedFaction" --out modulesheet
harvestWithout a file, harvests every source in the manifest library\sources.json (folders, file patterns, a group name for each, and packfiles to mount together). With a level or packfile, harvests just that into --group. --out names the library folder; it may not be, contain, or lie inside a source folder. The same sources always produce the same files.
list, show, statsBrowse the library: filter by --category, --attach, --role, --style or --group; show <id> prints one module in full; stats counts modules by category, style and group, and your curation (kept, rejected, relabelled, undecided). list --include-rejected also lists the modules you rejected. Add --json for machine-readable output.
sheetDraws every selected module on its own — lit, in a three-quarter view, against a plain grey floor and the wall it mounts on — to <out>\thumbs\<id>.png and writes <out>\index.html, a contact sheet you open in a web browser. The best --top modules of each category are shown (24 by default; --group, --category and --style narrow the selection, --size sets the thumbnail size in pixels). Modules with textures from a level's own packfile are drawn with them when that packfile is still where it was harvested from. A card warns when a module would not show where it is placed (it lies behind its wall, or its brushes face inward).

Curating the library. The harvest sorts modules by rule, so some land in the wrong category or are not worth keeping. Open the sheet's index.html and, for each card, choose Keep or Reject (or press K, R or U with the mouse over it), correct its category, role or styles, and add a note. Filters at the top show one group, category or style, or only the cards you have not decided yet. Your choices are kept in the browser until you click Download curation.json; save the file as library\modules\curation.json (the download already includes everything the previous file held). Glacier applies it whenever the library loads: rejected modules are no longer offered to scripts, the design kit or the module tools, a corrected category, role or style replaces the harvested one, and kept modules are preferred (they rank 0.5 above their harvest score). A harvest never changes curation.json; it reports entries that name modules the new harvest no longer produced. Entries with an unknown id or value are skipped with a warning.

Where the library lives. Glacier looks for it in this order: the folder given with --modules (the modules commands) or the GED_MODULE_LIBRARY environment variable (every command, scripts and the editor); then library\modules beside the program; then library\modules in the folder that holds Glacier.sln when running from a source checkout. With no library the detailing functions still work: they build simpler parts of their own and say so in their result (fallback = true). Modules that use textures from a level's own packfile are only offered when those textures are available to the level being built.

13. AI-assisted level design

An AI agent that can run command-line programs, such as Claude Code, can build and edit levels for you through glacier-cli and the design kit. You describe what you want; the agent writes a Lua script, runs it, draws the result as a floor plan, checks it, and reports back. It assists — it does not replace you. You direct it, review what it made, and keep shaping the level with further requests, by hand, or both.

Block out

Rooms, corridors, doorways, stairs, ramps, platforms, pillars, sliding doors and outdoor skies, built from plain brushes on a clean grid; whole spaces from an archetype library, bridges, landmarks, and textured walls with trims.

Populate

Lights under fixtures, props, cover and decals, multiplayer spawns, items, the Player Start, triggers and links, level properties.

Check

Sealed builds, hole checks, the linter, floor-plan images and structured level summaries, so the agent can verify its own work.

Edit

Find and change existing objects and brushes — by name, tag, area or your current selection.

Everything the agent makes is ordinary editor content: simple brushes, named objects, and named groups for multi-part pieces such as stairs. Nothing is locked away; you can select, move, re-texture or delete any of it as usual.

Connecting Claude Code (MCP)

glacier-cli mcp runs Glacier as a Model Context Protocol (MCP) server. An assistant that supports MCP — Claude Code, Claude Desktop and others — then gets Glacier's operations as tools: it can open, script, build, check, render and save levels and look at the floor plans it draws, without typing commands into a terminal. The assistant starts the server itself and talks to it over standard input/output; nothing listens on a network port.

Claude Code. Run this once in a terminal, with your Glacier folder in place of C:\Games\Glacier:

claude mcp add glacier -- "C:\Games\Glacier\glacier-cli.exe" mcp

Watching and undoing

  • One run, one undo step. Each script the agent runs in the editor is a single undo step labelled CLI: <script name> (AI: <script name> through the MCP tools). Ctrl+Z removes the whole run; a script that fails changes nothing.
  • The agent can take back its own runs. glacier-cli undo --attach undoes the latest command-line run, and refuses when your own edit is the latest step — an agent never undoes your work.
  • Live output. The agent's messages appear in the Script Log, and the viewport updates when each run finishes.
  • Pictures it can read. The agent checks layouts with floor-plan images (Rendering images). Ask it to show you the image it looked at.

Finding what the agent made

Everything an agent's run creates is tagged ai.script (the script's file name) and ai.session (one id per command it ran). Design-kit parts are also tagged kit, kit.name (the name of the room, door, stairs…) and kit.part. glacier-cli summary counts the tags; in the Script Console:

level.brushes_tagged("ai.session"):select()        -- every brush an agent created
level.objects_tagged("ai.session"):select()        -- every object an agent created
level.brushes_tagged("kit.name", "hall"):select()  -- the parts of the room named "hall"

Tags are saved with the level and do nothing in the game.

Everything the kit places for a reason also carries kit.role — cover, route, landmark, theme_detail or fixture — and kit.purpose, a sentence saying what it serves: the sightline a cover cluster breaks, the places a bridge joins, what can see a landmark, the theme and space a prop dresses. kit.roles{} lists them, and level.brushes_tagged("kit.role", "cover"):select() selects all the cover. The kit refuses elements without a purpose — a bridge whose ends are already joined by the floor below, stairs or another crossing, a landmark nothing can see, boulders on a built room's floor, a flight of stairs that climbs into a wall, onto a box or beside another way up to the same floor — and the design grader's function checks (G27–G31) find such elements in any level: bridges that serve no route, misplaced rocks, cover with nothing to break, stairs that lead into a wall, onto nothing or down into a dead-end pit under a bridge, and doorways or corridors where the route between two floors makes players hop a step instead of walking a ramp or stairs.

Caves, canyons and rocks

Besides rooms on a grid, the design kit builds natural spaces along a floor path on any heading: kit.cave (a rough rock tunnel), kit.canyon (open to the sky, with leaning walls and basins where you widen it) and kit.passage (a clean, level corridor at any angle), plus kit.rock_wall, kit.boulders and kit.pit for rock dressing and drops, and kit.light_path to light a route. Ask an agent for “a cave that climbs from the hub to a gallery” or “a canyon with two basins and some boulders” and it uses these.

  • Walkable by construction. Every cave and canyon keeps a 1.8 m wide, 2 m high walkway along its path. Floors are level or a smooth slope of at most 45° on each stretch — no steps — with a short level landing where a climbing stretch turns.
  • Watertight and editable. Each space is a chain of plain convex brushes that meet on identical faces, grouped and tagged under the name the script gave it. Boulders and rock walls are detail brushes unless the script asks for a structural ridge. Change a generated space by running its script again with new options rather than moving its vertices by hand.
  • Repeatable. Each piece takes a seed: the same options and seed always give the same rocks; a new seed gives new shapes in the same layout.
  • Keep it central. Keep large caves and canyons within about 200 m of the level's origin; geometry far from it is compiled less precisely.
  • Within the lightmap budget. A level holds at most 32,767 lightmap surfaces (Alpine RED's limit), and every rock facet a player can see takes one. Traced rock and rock masses share one level-wide budget (kit.defaults.organic_budget): full facets near the floor, coarser cells higher up, coarser still when the level's rock would not fit. When a level would pass the cap, faces nobody can see (inside neighbouring rock or the wall) give up their surfaces first; any lit faces still left without one are listed by the build, the save log and the linter, and level.stats() counts them.

Two complete examples ship in the scripts library's examples folder and appear under Scripts ▸ Examples: snaking canyon (kit-canyon.lua, a 240 m outdoor canyon with basins, a descent, rock outcrops, a walkable ledge, boulders, lights, spawns and items) and cave network (kit-cave.lua, a hub with a cave climbing to a gallery, a passage to an armoury, and a loop down a pit and back up an underpass). Run either on a new level, then build, light and play it.

Brush or terrain ground

Open outdoor ground can be built from brushes or as an Alpine terrain. The design kit's kit.ground makes that choice for one area and records the reason: it picks terrain only when the area is large (at least 400 m² and 16 m across), open to the sky, needs no overhang, is natural ground rather than a built deck or room, and the level already targets Direct3D 11 (the Require Direct3D 11 or D3D11-only lightmaps setting in Level Properties, or a terrain already in the level). Canyon walls, caves and built floors always stay brushes. An agent can also ask for terrain or brush ground outright, or only ask for the decision and its reasons without building anything.

  • What the kit builds. A terrain over the area with gentle mounds that level out at its edges, at doorways and landings and under anything standing on it; worn paths between the openings and rock on the crests, painted as terrain layers; holes outside the area's outline and where openings are cut. It rests a few centimetres above the brush floor it covers.
  • Always sealed. A terrain does not seal a level, so the kit keeps it inside air: an outdoor room, an open-air layout's sky, or a sky volume it adds around a terrain built over open space.
  • In a layout. Asking kit.layout for terrain ground gives the natural platforms (isles and gardens) of an open-air layout a terrain top; built platforms keep their decks. The layout itself (its areas, connections and objectives) is the same as with brush ground.
  • Checked like any floor. After a build, the level checks treat the terrain as floor: spawns stand 1 m above it, the design grader and reachability checks walk on it, and a spawn placed under the terrain's surface is reported as inside the ground.
  • On other renderers a terrain shows each cell's main texture without Alpine's terrain lighting, which is why the automatic choice wants a Direct3D 11 level.

Planning a whole level first

For a whole level, an agent following the guide starts from a layout plan rather than from rooms: kit.layout turns a request (game mode, number of players, indoor or floating platforms, a one-line brief, a seed) into a list of areas — each with its kind of space, size, floor level and texture palette — the connections between them (corridors, doorways, stairs, ramps, drops, bridges, windows, lifts) and where the spawns, flags, hill or payload track go. The agent can show you the plan as a text drawing, change it, and check it against the layout rules before anything is built; kit.build_layout then builds it watertight, with lights, spawns and the game-mode setup (CTF flags, a King of the Hill capture point, or a Payload cart with its checkpoints and spawn hand-off) in place.

  • Sized for the players. A 2–4 player arena is about 1,500–3,000 m² of floor; 8 players about 3,300–4,900 m²; 16 players up to about 6,400 m². CTF and King of the Hill maps are larger, and Payload maps are three to five legs long. A Payload cart route can run and turn on any heading and cross a chasm on a cart bridge.
  • Composed like a building. Rooms of very different sizes share walls, wings stand at an angle, corridors bend and odd-shaped rooms fill the corners between them. CTF halves mirror each other, a King of the Hill hill sits inside a ring of rooms, a Payload track turns a corner inside a yard and bends between its legs, and open-air platforms stand at free angles round a central one.
  • From a sketch. An agent can also trace a sketch or concept image into the same plan: each area becomes an outline in metres and each connection follows the sketch's bends; the plan is then checked and built the same way. Keep a traced plan within about 450 m of the level's origin, where angled geometry builds watertight.
  • Finished like a mapper's rooms. Once the geometry stands, every area is detailed by default from its kind and texture palette: pilasters and trims along the long walls, frames round the doorways, beams under roofed ceilings (never under open sky), railings along gallery edges, raised floors and bridge decks that drop away, handrails on stairs, and rock formations in cave areas — taken from the module library when it is installed, otherwise built from plain stock-textured parts, and kept clear of doorways, routes, stairs, spawns and the Payload cart's track. A pit room is a deep chasm crossed by its bridge, with no stairs down into it. The agent can turn the pass off (detail = false) or leave out single parts.
  • Loops, not dead ends. Every area has at least two ways in and out (one small reward room at most), routes loop, the level spans at least three storeys, CTF bases have three exits on two heights with three lanes between them, a King of the Hill hill is sunken or raised with five to eight approaches, and every Payload checkpoint has three routes into the next leg.
  • Repeatable. The same request and seed give the same level; a new seed gives another layout. Everything built is ordinary, tagged, hand-editable brushes and objects.
  • Not yet dressed. The layout places spawns and the game-mode objects but no items, crates or decals; ask the agent to populate it afterwards. Every area of the plan keeps its name, so the dressing, item and spawn helpers can be pointed at it by that name.

Safety

  • Destructive operations need your permission. Deleting content, overwriting another file, or discarding unsaved changes in the editor is refused unless the command carries --allow-destructive. Agents following the guide only use it when you asked for that change. Through the MCP tools in the editor, the server must be started with --allow-destructive and Settings ▸ General ▸ Allow destructive AI actions must be on.
  • Limited places to write. Files are written only under the level's folder, your install's user_maps, the scripts library, or — for headless work — paths named on the command line. Scripts have no file, network or process access.
  • Local only. The editor connection belongs to your user account on this computer; it is never a network port.

Example requests

  • “Block out a small deathmatch level: two 14 m rooms joined by a corridor, two pillars, eight spawns, a shotgun and a medkit. Show me the floor plan, then build it, check it for holes, light it and save it.”
  • “In the open editor, add a raised platform with stairs in the corner of the room I have selected, and light it.”
  • “Summarise this level: which rooms have no lights, and which spawns are too close to a wall? Don't change anything yet.”
  • “Add a sliding door with Use buttons on both sides to the doorway between hall and annex.”
  • “Run a cave from the west wall of the hub up to a new room 6 m higher, scatter a few boulders in it, check it for holes, and light it.”
  • “Dress the hall and the yard as an industrial area, then place eight spawns and the items for team deathmatch.”

Limitations

  • Check in the game. The agent verifies geometry, holes, the linter and the layout, but not how the level plays. Play-test it — especially doors: a design-kit door's timing and blocking are only confirmed by playing.
  • Portals are opt-in. The agent adds visibility portals only where you ask for them; small levels play fine without.
  • Spatial judgement. Agents reason about space from plans and numbers. Review the floor plan of every storey, and say exactly what you want moved and where.

14. Playtesting

Launch straight into your level through Alpine Faction. Play Level (F7) and Play Level from Camera (F8) start single-player; Play in Multi (F9) and Play in Multi from Camera (F10) start a multiplayer session. The "from Camera" variants spawn you at the current viewport camera's exact position and heading, in both single-player and multiplayer — Glacier passes the pose through the game's own launch switches, so the first spawn lands where the camera looks.

Playtesting saves your level first, RED-style: the save writes exactly what you last built and does not re-bake, so run Geometry ▸ Build and Build ▸ Calculate Lighting before playtesting if you have changed geometry or lights. (Unsealed live-preview geometry is re-sealed automatically before the save, which resets its lightmaps to unbaked.)

Play-tests run through AlpineFactionLauncher.exe. On Linux the launch goes through a configurable template (default wine {exe} {args}) so the Windows launcher runs under Wine or Proton; staging paths flow through the VFS mount unchanged.

15. Import & export

Importing meshes

File ▸ Import Mesh brings in OBJ, FBX, glTF/GLB and DAE geometry, with a scale/axis/winding wizard. Import as one brush per material group, or as a batched static mesh object.

Exporting

Export the level or a selection to OBJ, glTF and VRML, or convert selections to mesh objects.

Packaging

The VPP packfile builder (File ▸ Create Level Packfile) collects your level and its referenced assets into a distributable .vpp, using the dependency scan to find what the level needs. It writes <level name>.vpp in the level's own folder without asking, and replaces that packfile in place when it already exists. It packs the level as it is now: unsaved changes are saved first (with the normal save rules), and the packfile carries the saved .rfl file, so the packed level and the loose one are identical. A level that has never been saved must be saved first. When a referenced file is missing, the review dialog opens instead so you can decide what to pack. File ▸ Create Level Packfile As… always opens the review dialog, where you can choose which files to include and pick another output path. Scripts get the same behaviour from ops.package().

Stale packfiles. Red Faction loads a level from a packfile before a loose .rfl of the same name. If mylevel.vpp next to mylevel.rfl still holds an older copy of the level, the game plays that copy, not your latest save. Every save (editor, script or command line) notes this in the Log panel when it happens; rebuild the packfile with Create Level Packfile, or delete it, before testing. Play Level checks its staging folder the same way.
RFL versions. Glacier loads .rfl files from versions 180–306 and always saves version 306 (the Alpine Faction 1.5 format). Opening a pre-Alpine (<300) level shows a non-blocking informational notice; an older level is upgraded when saved, and the Log panel lists anything the upgrade changed (for example a fog near clip reset to 0, or Looping sound events that now loop). A level saved by a newer Alpine Faction opens read-only — Glacier shows a notice, marks the window title, and refuses to save it so its newer content is not lost.
Alpine Faction 1.5 objects. Weather regions, vehicle factories, projection cameras, rope emitters, directional lights and vehicle waypoint helpers are placed and edited like any other object, and so is terrain (see Objects & events). A level's terrain is written back exactly as it was saved until you change it. A few levels saved by pre-release Alpine Faction builds store one of these object lists in a layout Glacier does not fully read: that list is kept unchanged, its objects are read-only (the Properties panel says why), and new objects of that kind cannot be added to the level.
Alpine lightmaps. A level lit in Alpine RED can carry Alpine Faction's Direct3D 11 lightmaps alongside (or, with "D3D11-only lightmaps", instead of) the stock lightmaps. Glacier keeps them unchanged until it rebuilds the geometry or recalculates the lighting. Calculate Lighting with the Alpine pipeline (see Lighting) bakes new Alpine lightmaps, which the next save writes in their place; any other rebuild or relight means they no longer match the level, so saving drops them with a note in the Log panel and the game uses the stock lightmaps Glacier wrote. The level's D3D11-only and Require Direct3D 11 flags are updated to match: Glacier always writes the stock lightmaps as well, so a D3D11-only level gets stock lightmaps from its next Calculate Lighting. Glacier's viewport shows Alpine lightmaps and terrain light charts, whether Glacier or Alpine RED baked them.
New levels start with Alpine RED's new-level settings: Legacy Cyclic Timers and Legacy Movers off, every other Alpine level property at Alpine's defaults. Levels you open keep their own settings; one without Alpine level properties keeps the stock behaviour (legacy timers and movers on) until you change one. The Gameplay tab of Level Properties also holds the Payload rules (push speed, rollback, acceleration, checkpoint bonus, heal and ammo, overtime grace, respawn delay modifiers); a Payload cart needs Legacy Movers off, and the linter checks everything else Alpine Faction requires of the cart and its checkpoints.

17. Troubleshooting & FAQ

Textures and meshes show as missing / pink

The Red Faction install folder is not set or does not contain the expected VPPs. Set it in Settings ▸ General, then Tools ▸ Reload Textures. Verify All Textures lists exactly which faces are unresolved.

Play-testing does nothing / can't find the launcher

Play-tests run through AlpineFactionLauncher.exe. Point Glacier at it in Settings (it is auto-detected from the af:// protocol registration). On Linux, check the launch template (default wine {exe} {args}).

Linux: Glacier won't start after extracting the tar.gz

The tar.gz is packaged on Windows, which cannot preserve the Unix executable bit. After extracting, run chmod +x Glacier once, then launch it. The AppImage does not need this — it is already executable.

My build has a leak / open edges

Run Check for Holes. Hole-leak findings in the build report are click-to-navigate — click one to frame the leak. Confirm surrounding brushes are Solid (not Detail) and that the shell is sealed.

An old level won't save the way it loaded

Glacier loads RFL versions 180–306 and always saves version 306 (Alpine Faction 1.5 format). Opening a pre-Alpine level is fine — it is upgraded on save. Levels from a newer Alpine Faction open read-only.

A camera key won't rebind

Continuous camera movement (pitch / heading / slide / move / zoom / ortho zoom) uses fixed held keys by design and is not rebindable. Everything else is rebindable in Settings ▸ Input.

Where are my settings stored?

Next to the app when its folder is writable (portable). If the folder is read-only (e.g. installed under Program Files), Glacier falls back to your user profile and shows a one-time notice — nothing is lost.

Where can I get help or share levels?

Join the community on Discord. The Report Bug button in Help ▸ About opens the issue tracker in your browser.
